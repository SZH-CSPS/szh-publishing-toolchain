# Draw stretched spaces next to the previous glyph

## Problem

In justified text, and with `word-spacing`, Chrome and Edge (PDFium) extract some lines with words glued together, "states the levels" becoming "statesthelevels", and so do the screen readers that use their text layer.

The space glyphs are in the PDF, but each one is drawn in the middle of its gap. To justify, WeasyPrint stretches each space with a Pango `letter_spacing` attribute (`text/line_break.py`, `Layout.set_text()`). Pango gives half of this extra width as the `x_offset` of the space glyph, and `draw_first_line()` (`draw/text.py`) writes this offset in the `TJ` array before the glyph, and the rest after it:

```
[<states> -273.148 < > -260 <the> -273.148 < > -260 <levels> …] TJ
```

PDFium sees a gap between "states" and the space, inserts a generated space (`FPDFText_IsGenerated()` is true) and then drops the real space, which follows too closely.

```html
<html lang="en">
<style>@page { size: A5; margin: 15mm } body { font: 11pt "DejaVu Sans" }</style>
<p style="text-align: justify">Participation is measured by what each pupil can do, and not by what the school lets them watch. Adjustments are discussed with the family and written down in a plan that states the levels and the measures.</p>
<p style="word-spacing: 4pt">Word spacing goes through the same code.</p>
```

## Fix

In `draw_first_line()`, for a space (U+0020 or U+00A0) with an `x_offset`, in a text that is justified or has `word-spacing`, nothing is written before the glyph and the offset is added to the number written after it:

```
[<states > -533.148 <the > -533.148 <levels > …] TJ
```

The following glyphs keep exactly the same position and spaces have no ink, so the rendering is the same. Other glyphs, spaces with a `y_offset`, and spaces of text that only has `letter-spacing` keep the current drawing.

## Spec references

- ISO 32000-1:2008, 9.4.3 (Text-Showing Operators): numbers in a `TJ` array only move the next glyph; writing the offset after the space instead of before gives the same glyph positions.
- ISO 32000-1:2008, 14.8.2.5 (Identifying Word Breaks): a space character (U+0020) is the explicit way to mark a word break; extractors that guess word breaks from gaps are expected to rely on it.
- ISO 14289-1:2014 (PDF/UA-1), 7.2 (Text): text is mapped to Unicode so that assistive technologies can extract it. Here the spaces are mapped, but PDFium discards them because of their position. veraPDF can't see it.

## Before / after

Rendering the example above with WeasyPrint 70.0 and reading it with pypdfium2 (· real space, ◦ space generated by PDFium):

```
Before: states◦the◦levels◦and◦the◦measures.◦Participation◦is·
        Word◦spacing◦goes◦through◦the◦same◦code:◦each·
        19 generated spaces, 49 real spaces
After:  states·the·levels·and·the·measures.·Participation·is·
        Word·spacing·goes·through·the·same·code:·each·
        0 generated spaces, 68 real spaces
```

Identical pixels at 150 and 300 dpi (pypdfium2), veraPDF `--flavour ua1` passes before and after. pypdf, which adds its own space before a large gap, read these lines with double spaces before ("states  the  levels") and reads them with single spaces after; its words are the same.
